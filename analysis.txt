SORTING FIXED-LENGTH SOCIAL MEDIA IDS
=====================================

PROBLEM STATEMENT
Sort the IDs 324, 125, 456, 218, 102, 389, 275, 147 using Merge Sort and Quick Sort. Record execution steps and compare operations, complexity, and additional space.

C. COMPARISON
-------------
Merge Sort:
- Best time: O(n log n)
- Average time: O(n log n)
- Worst time: O(n log n)
- Additional space: O(n)
- Stable: Yes

Quick Sort:
- Best time: O(n log n)
- Average time: O(n log n)
- Worst time: O(n^2)
- Additional space: O(log n) average recursion space; O(n) worst case
- Stable: Usually no

CONCLUSION
----------
Merge Sort is appropriate when guaranteed O(n log n) time and stability are important. Quick Sort is often fast in practice and generally uses less auxiliary memory, but poor pivot choices can lead to O(n^2) time. For fixed-length numeric IDs when sorting by digit positions is specifically desired, Radix Sort is another suitable option.

NOTE
----
The phrase "after each digit position is processed" describes Radix Sort, not Merge Sort. The Merge Sort trace above records merging passes. Quick Sort's exact intermediate arrangement depends on the partition implementation; the trace above matches the last-element-pivot Lomuto code included in quick_sort.c.
